1. About This Portfolio

This e-portfolio explores my learning and development in intelligent agents. It considers how agent-based systems can support complex tasks, how a proposed design translates into a practical implementation, and why safety, explainability and responsible deployment are essential to the development of artificial intelligence.

The portfolio focuses on the Academic Evidence Investigator, a proposed intelligent research assistant. Through this project, I consider the opportunities and limitations of using language models and agent-based workflows to support academic research.

The portfolio also reflects on the relationship between technical functionality and trustworthy results. A system may execute a workflow successfully without necessarily producing accurate or reliable information. Understanding this distinction is important when evaluating intelligent agents.

2. Project Overview: Academic Evidence Investigator

The Academic Evidence Investigator was proposed as an intelligent research assistant for postgraduate students and early-career researchers. Its intended purpose is to help users organise research questions, identify potentially relevant literature, examine evidence and prepare structured summaries.

Academic research involves more than locating information. Researchers must evaluate the credibility of sources, identify gaps in the literature, distinguish evidence from interpretation and recognise uncertainty. An intelligent assistant could help organise these tasks, but it should not replace independent reading or academic judgement.

Proposed multi-agent architecture

Planner / Supervisor Agent

The planner is intended to translate a research question into smaller tasks, coordinate the workflow and determine the next appropriate action. Planning can make a complex research process more structured and manageable.

Retrieval Agent

The retrieval agent is intended to locate potentially relevant academic publications through services such as Semantic Scholar and Crossref. Retrieved records need to be checked for authenticity, relevance and bibliographic accuracy before being used.

Evidence Analysis / Critic Agent

The critic agent is intended to examine the available evidence, identify gaps or inconsistencies and recommend further investigation when the information is insufficient. This role is important because an answer should not be considered reliable simply because it sounds convincing.

Reporting Agent

The reporting agent is intended to organise findings into a structured output, distinguishing supporting information from interpretation and unresolved questions. Clear reporting can help users assess the strength of the conclusions.

Purpose and expected value

The proposed system aims to make early-stage literature investigation more organised. By separating planning, retrieval, evidence analysis and reporting into different responsibilities, the design provides a framework for considering how different tasks can be coordinated.

However, dividing work among agents does not automatically make a system more accurate. The quality of the result still depends on the quality of the source material, the decisions made during the workflow and the effectiveness of the evaluation process.

3. Design and Implementation

Original design proposal

The original group proposal considered a multi-agent architecture using LangGraph to coordinate tasks. It proposed Qwen2.5-7B through Hugging Face for language-model capabilities, Semantic Scholar and Crossref for literature discovery, JSON for structured information, SQLite for storage and Flask for a possible web interface.

The proposed architecture separated research planning, source retrieval, evidence evaluation and reporting. This separation provided a conceptual structure for the project and made the responsibilities of the intended agents easier to describe.

Practical implementation

The local starter project, named llm_planning_agent_starter, was executed in a Python virtual environment. The recorded program accepted a research goal and produced a plan, candidate source records, a synthesis and an action trace.

The recorded run used a deterministic fallback rather than verified live language-model inference. Live hosted inference remained unverified because the Hugging Face authentication token was invalid. The candidate source records included synthetic placeholder data, so they cannot be treated as verified academic publications.

Comparing the design with the implementation

The original design described a broader multi-agent research assistant, while the practical implementation demonstrated a more limited local workflow. The distinction is important because proposed functionality should not be presented as functionality that has already been implemented and tested.

The planning workflow demonstrated how a research goal could be converted into a sequence of actions. The output also showed how candidate records and a synthesis could be represented in a structured process. These results illustrate a starting point for development rather than proof of a complete research assistant.

The proposed retrieval capability was not fully demonstrated by the placeholder records. Similarly, the existence of an intended evidence critic does not by itself establish that the system can reliably detect weak evidence or contradictions. These capabilities require implementation and appropriate testing.

The local test suite recorded six passing unit tests. This indicates that the tested functions passed those tests in that run. It does not establish that every possible input is handled correctly, that sources are genuine or that generated conclusions are accurate.

Technical challenges and learning

One challenge was the distinction between successful software execution and trustworthy research results. A program can complete its workflow while still relying on inaccurate or synthetic information. This means that technical testing and evidence validation address different questions.

Another challenge was hosted-model authentication. The inability to verify live inference limited the conclusions that could be drawn about the language-model integration. Resolving this would require valid authentication, secure configuration and additional testing.

Overall, the development process highlighted the importance of reporting limitations accurately. A credible evaluation should explain what was demonstrated, what remains uncertain and what would need to change before the system could be used for real academic research.

4. Reflective Case Studies

The following case studies consider three themes in responsible intelligent-agent development: AI safety constraints, explainable decisions and responsible deployment. Each reflection follows the What? So what? Now what? structure associated with Rolfe, Freshwater and Jasper (2001).

Case Study 1: AI Safety Constraints

What?

The Academic Evidence Investigator is intended to support users who are investigating academic questions. Such a system may produce incorrect claims, misinterpret source material or present uncertain information too confidently. The local prototype's use of placeholder records illustrates why generated outputs should not automatically be treated as reliable evidence.

So what?

This raises an important safety issue. In academic work, an inaccurate citation or unsupported claim can undermine the quality and integrity of a student's work. If an agent continues through several stages without checking its evidence, an initial error may influence the final report.

Reflecting on this problem helped me distinguish technical autonomy from trustworthy autonomy. A system may be able to complete several steps independently, but that does not mean every decision should be left to the system. The appropriate level of autonomy should depend on the quality of the available information and the consequences of an incorrect decision.

The project also demonstrates why testing the workflow is not enough. Passing unit tests does not establish that a source exists or that an interpretation accurately represents a publication. Software behaviour and evidence quality must therefore be considered separately.

Now what?

I would introduce stronger source validation, record the origin of important claims and make uncertainty visible to users. The system should request human review when it cannot verify an important piece of information. Testing should include irrelevant sources, contradictory evidence, missing information and malformed records.

I would also assess whether the system communicates its limitations rather than producing a confident but unsupported answer. These measures would help make the workflow more cautious and improve the reliability of its outputs.

Case Study 2: Explainable Decisions (XAI)

What?

An intelligent research assistant may decide how to divide a research goal, which records to consider, what evidence to summarise and when to recommend another search. Users need enough information to understand these decisions and evaluate the resulting output.

So what?

A fluent or well-organised answer is not necessarily an explainable one. If a system does not show why it selected a source or how a claim relates to the available evidence, users may struggle to identify mistakes. This is particularly important in academic work, where claims should be traceable to credible sources.

The local program's action trace provides a starting point for making workflow steps visible. However, a record of actions does not prove that the reasoning or conclusions are correct. An explanation must be connected to information that a user can independently examine.

This reflection changed how I understand transparency in intelligent systems. Showing what the system did is useful, but users also need to understand the basis of important conclusions and recognise where uncertainty remains.

Now what?

I would provide source details and explain the purpose of each major stage. Where possible, individual claims should be linked to supporting passages. The system should distinguish retrieved information from generated interpretations and unresolved questions.

I would evaluate explainability by checking whether users can identify the sources behind a conclusion, recognise uncertainty and challenge an incorrect result. This would make explainability a practical evaluation requirement rather than simply a feature of the interface.

Case Study 3: Responsible Deployment

What?

The proposed research assistant could help organise early-stage literature investigation. However, its outputs could be misleading if records are synthetic, outdated, irrelevant or incorrectly summarised. Users may also become overly dependent on automation when its limitations are unclear.

So what?

Responsible deployment requires considering how a system is used in practice, not just whether the software runs. A prototype that works in a controlled demonstration may behave differently when it receives real research questions and incomplete evidence.

The distinction between the original proposal and the practical implementation also matters. It would be misleading to describe proposed features as completed features or to claim that research results are accurate without suitable evaluation. Honest reporting of limitations is part of responsible development.

Responsible use also involves considering privacy, data handling and the potential consequences of users relying on generated material. Academic users should be able to understand the role of the system and remain responsible for evaluating its output.

Now what?

Before wider deployment, I would evaluate the system with representative research tasks, use genuine and verifiable source records, document known limitations and establish a process for identifying and correcting errors. Users should remain responsible for checking sources and deciding whether conclusions are suitable for academic use.

I would also review privacy and data-handling practices, particularly if users submit unpublished research or personal information. Deployment should follow relevant institutional guidance and take account of risks identified during testing.

Overall reflection

These case studies demonstrate that developing an intelligent agent involves more than implementing a workflow. Reliability, transparency and responsible use are also essential. The project helped me recognise that the proposed capabilities of a system must be distinguished from what has actually been demonstrated. Future development should combine technical testing with careful evidence validation, critical evaluation and human oversight.

5. Future Development

The Academic Evidence Investigator could be improved through several development priorities.

Improving evidence quality

Candidate records should come from genuine academic sources and include verifiable bibliographic information. Claims in generated summaries should be linked to supporting evidence where possible.

Completing and evaluating model integration

Hosted-model authentication would need to be configured securely and live inference verified. Additional tests should evaluate how the system responds to ambiguous questions, irrelevant sources and contradictory information.

Strengthening explainability

The system should make its major actions, source choices, uncertainty and limitations clear. Users should be able to trace important claims back to the evidence used to support them.

Responsible use and oversight

Further development should include evaluation of privacy, data handling and the consequences of incorrect outputs. Human review should remain available for important decisions, especially when evidence is incomplete or uncertain.

These improvements would help move the project from a limited demonstration towards a more reliable and transparent research assistant.

6. Conclusion

The Academic Evidence Investigator provided a context for examining the relationship between intelligent-agent design and practical implementation. Its proposed architecture separates planning, retrieval, evidence analysis and reporting into distinct roles.

The local implementation demonstrated a limited workflow and recorded six passing unit tests. However, deterministic fallback behaviour, unverified live inference and synthetic candidate records limit what can be concluded about its real-world research capabilities.

A central learning point is that an intelligent agent should not be evaluated only by whether it completes a task. Its evidence, uncertainty, safety boundaries and influence on human decisions also matter. Technical functionality must be considered alongside accuracy, explainability and responsible use.

Overall, this project strengthened my understanding of the difference between a proposed intelligent system and an implementation supported by evidence. It also highlighted the importance of human oversight and critical judgement when applying artificial intelligence to academic research.
