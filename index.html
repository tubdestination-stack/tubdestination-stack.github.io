2. My Project: Academic Evidence Investigator

The Academic Evidence Investigator was proposed as an AI-assisted research tool for postgraduate students and early-career researchers. Its intended purpose was to help users break down a research question, identify potentially relevant literature, consider evidence quality and produce a structured research briefing.

The original group proposal described four specialist roles: a Planner/Supervisor Agent, a Retrieval Agent, an Evidence Analysis/Critic Agent and a Reporting Agent. The design aimed to divide the work into manageable stages and support human review of the resulting research briefing.

The project helped me understand that an intelligent agent involves more than generating a response. A workflow can plan actions, process information, record intermediate results and provide outputs that can be inspected and tested.

3. Comparing the Proposed Design with the Implementation

Proposed design

The group proposal described a multi-agent architecture using LangGraph for orchestration, a configurable Qwen model through Hugging Face, Semantic Scholar and Crossref for academic retrieval, JSON for structured information, SQLite for persistence and Flask for a user interface. It also proposed further searching when evidence was weak or unbalanced.

Demonstrated implementation

The available local implementation accepted a research goal, generated a plan, returned candidate source records, produced a synthesis and recorded an action trace in a JSON file. The local program ran using deterministic fallback behaviour.

Six unit tests were reported as passing. However, live hosted LLM inference and genuine academic retrieval were not verified. The candidate records used in the demonstration were synthetic placeholders, not confirmed academic publications.

This comparison shows why it is important to distinguish the original design from the features that were actually demonstrated. A proposed feature should not be described as implemented unless there is evidence to support that claim.

5. Reflective Case Studies

The following reflections use Rolfe et al.’s (2001) framework: What? So what? Now what?

Case Study 1: AI Safety and Bounded Autonomy

What?

The proposed system was intended to support researchers rather than replace their judgement. Its design separated planning, retrieval, evidence analysis and reporting. The local demonstration exposed intermediate stages and an action trace. However, the available evidence does not establish that all proposed safety controls or the critic-driven re-planning loop were implemented.

So what?

An autonomous system can produce convincing-looking output even when its evidence is incomplete. In academic work, an unsupported summary could mislead a researcher or encourage an unsuitable citation. Recording actions makes execution easier to inspect, but it does not prove that the system's decisions are correct. Human oversight is therefore important.

Now what?

I would introduce explicit stopping conditions, warnings when evidence is missing and a human approval step before a briefing is used as research evidence. I would test these safeguards using empty results, malformed records and conflicting sources. These are proposed improvements, not claims about features already implemented.

Case Study 2: Explainable AI Decisions

What?

The demonstrated pipeline produced a plan, candidate records, a synthesis and an action trace. It also saved a JSON run record. The implementation used a simple keyword-overlap baseline to match a goal to candidate records rather than verified semantic search.

So what?

Visible intermediate steps make a system easier to inspect and help a developer investigate unexpected results. However, visibility is not the same as a complete explanation. Keyword overlap can identify records containing similar words without showing that the records are relevant or scientifically reliable. A saved execution record is evidence of what ran, not proof that its conclusions are accurate.

Now what?

I would record why each source was selected, retain source information alongside each claim and distinguish source-based evidence from generated interpretation. A human reviewer could then check whether the explanation is understandable and whether the original source supports the associated claim.

Case Study 3: Responsible AI Deployment

What?

The local run used synthetic demonstration records and deterministic fallback behaviour. An attempt to access Hugging Face failed because the token was rejected as invalid. Consequently, live hosted inference and genuine scholarly retrieval were not verified in the available evidence.

So what?

Presenting synthetic records as real publications would mislead users and undermine academic integrity. Similarly, describing fallback output as live model output would exaggerate what was tested. Responsible development requires honest reporting, protection of credentials and verification of evidence.

Now what?

Before deployment, I would verify publication details against original records, test live model access, record integration failures and protect API credentials. I would also label demonstration data clearly and require generated summaries to be checked before they are used in academic work.
